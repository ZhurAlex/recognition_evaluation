  Конфликты при выборе пар

  Допустим, каждый объект эталона просто ищет себе лучшего кандидата в разметке.

  эталона. Нужно правило «одна пара на объект». Обычно используют один из двух
  вариантов:

  1. Жадный. Посчитать IoU для всех пар, отсортировать по убыванию, брать пары
     сверху вниз. Если один из объектов пары уже занят, пару пропускаем. Просто
     и понятно, на плотных сценах иногда даёт неоптимальный результат.
  2. Венгерский алгоритм (scipy.optimize.linear_sum_assignment). Ищет такое
     разбиение на пары, при котором сумма IoU максимальна. Формально он
     оптимален.

  Для этой задачи достаточно жадного варианта. Подумай, нужен ли тебе
  венгерский, и сможешь ли ты обосновать выбор.

  Почему это важно. Если разметчик обведёт знак 0.6 идеально, по тем же
  координатам, что в эталоне, скрипт покажет 81%, а не 100%. Ошибка тем больше,
  чем меньше объект.

  1. Повторить правило инструмента для bBox. Срез numpy с округлением вниз:

     ради единообразия с полигонами. Теперь видно, что единообразие с Pillow
     здесь не главное: важнее совпасть с правилом, по которому сделан эталон.

  работает.

  Если обращение через имя класса смущает, есть альтернатива — @classmethod:

  @classmethod
  def generate_mask(cls, data, masks_dir):
      ...
      return cls._mask_from_path(...)

  Python передаёт первым аргументом сам класс, по аналогии с self для объекта.
  Так имя класса не повторяется внутри, а если когда-нибудь появится подкласс,
  переопределивший _mask_from_*, вызовется его версия. Для скрипта это скорее
  вопрос вкуса: оба варианта корректны.

❯ Как написать жадный алгоритм? Мы идем по каждому элементу списка и что мы
  делаем с индексами? Добавляем их в set? Тогда, тоеретически, у нас будет два
  сета и соответствующие элементы будут на соответствующих позициях

● Множества тут нужны, но не для того, о чём ты пишешь. Порядка элементов у
  множества нет, поэтому соответствие «по позициям» между двумя множествами
  получить нельзя. В каком порядке их обойти, Python не гарантирует.

  У множеств здесь одна задача: быстро отвечать на вопрос «этот индекс уже
  занят?» (i in used_gt). Сами пары хранишь отдельно, в списке.

  Что нужно перед циклом:
  - used_gt = set() — занятые индексы эталона;
  - used_ann = set() — занятые индексы разметки;
  - matches = [] — принятые пары, например кортежи (i, j, iou).

  Что делать для каждого кандидата (iou, i, j):
  1. Если i уже в used_gt или j уже в used_ann, пропустить.
  2. Иначе добавить пару в matches, а i и j — каждый в своё множество.

  Соответствие между индексами хранится в самом кортеже внутри matches.
  Множества лишь не дают взять объект второй раз.

  После цикла:
  - пропуски: set(range(n)) - used_gt;
  - ложные срабатывания: set(range(m)) - used_ann.

  Функции понадобятся n и m, потому что объект без единого кандидата (как эталон
  3) в списке кандидатов вообще не встречается. Узнать о нём можно только из
  общего количества объектов.

  1. Что значит «лучший»

  Без критерия на этот вопрос нет ответа. Алгоритмы оптимизируют разное:
  - жадный первым делом берёт самую уверенную пару и дальше её не
    пересматривает;
  - венгерский максимизирует сумму IoU по всем парам.

  Ни один не «правильнее» сам по себе. Сначала выбирается критерий, и только
  потом можно говорить, какой алгоритм лучше по этому критерию.

  2. Как проверить, что алгоритм делает то, что обещает

  Маленький пример, где алгоритмы расходятся. Его можно посчитать вручную:

             разм.0  разм.1
  эталон 0    0.9     0.8
  эталон 1    0.8     0.0

  - Жадный: берёт (0, 0) = 0.9. Дальше эталон 1 может пойти только к разметке 1,
    а там IoU 0. Получается 1 пара, 1 пропуск и 1 ложное срабатывание, сумма
    0.9.
  - Венгерский: (0, 1) + (1, 0) = 0.8 + 0.8 = 1.6. Две пары, ни одного пропуска.

  Результат здесь известен заранее, так что проверка честная. Заодно пример
  показывает, в чём разница на практике: жадный может оставить объект без пары
  из-за одной сильной пары, а венгерский старается сопоставить как можно больше
  объектов.

  Перебор всех вариантов. Для 8 × 8 объектов вариантов распределения 8! = 40
  320. Компьютер переберёт их за секунду. Перебор даёт точный оптимум для любого
  критерия, хоть суммы IoU, хоть нашей итоговой метрики. С ним можно сравнить
  оба алгоритма. Как проверка это надёжнее любого рассуждения, но для сдачи
  необязательно.

  3. На наших данных

  Если пары совпадут, вопрос «кто прав» здесь не возникает: оба критерия дают
  один ответ. Алгоритмы расходятся только на плотных сценах, где один объект
  сильно пересекается с несколькими. В таком случае расхождение — повод
  посмотреть на эти объекты глазами, например на скриншоте road.png, а не
  выбирать вслепую.

  Поэтому формулировка в отчёте вроде «алгоритмы дали одинаковые пары» — это уже
  полезный вывод, даже если ты не знаешь, какой из них лучший в общем случае.
