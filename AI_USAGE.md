## Как использовался ИИ

- ИИ разобрал формат входных данных и предложил план решения из шагов и варианты для каждого шага. Решения по каждому шагу принимал разработчик (см. таблицу решений).
- Работа велась в режиме ассистента: ИИ предлагал варианты, объяснял, проверял результаты на данных и делал ревью.
- Код, отвечающий за логику, разработчик написал сам, чтобы досконально понимать, как он работает: склейку JSON, класс `PictureObject` с построением масок из полигона и PNG, расчёт пересечений и объединений, кандидатов на сопоставление и итоговой оценки, структуру отчёта и `main`.
- ИИ разработчик поручал в основном механические задачи без сложных алгоритмов, код которых при необходимости легко проверить и поддерживать. Исключение — `greedy_matching`: алгоритм (порядок обхода, множества занятых индексов) разобрал разработчик, код по этому описанию написал ИИ.
- Фрагменты, которые ИИ написал по явной просьбе разработчика:
  - ветка bBox в `generate_mask` (правило растеризации, решение 11);
  - разбиение `generate_mask` на диспетчер и три метода `_mask_from_*` (решение 12);
  - `greedy_matching` (по алгоритму, разобранному разработчиком);
  - механический перенос кода по модулям (решение 15): логика не менялась, вывод сверен с прежним;
  - оркестратор `match_objects` и обновлённый `main`;
  - `build_message` в `report.py` (формат таблицы, решение 18); структуру `report.py` с разделением на построение текста и вывод в консоль и файл сделал разработчик;
  - исправление ширины колонок в шапке таблицы и `requirements.txt` (`pip freeze`);
  - `README.md`.
- Документ заполнялся по ходу разработки для документирования решений разработчика и использования ИИ.

## Особенности данных

- Полигоны хранятся по-разному. В `annotated` у полигона есть вершины в поле `path`. В `ground_truth` вершин нет, форма задана PNG-маской на весь кадр: `road.jpg.images/00001/<nm>.png`, 1000×667, 1 бит.
- Id объектов (`nm`) в эталоне и разметке не совпадают. Например, машина `0.1` в эталоне — это `0.3` в разметке, а в разметке есть id `0.9`, которого нет в эталоне: это машина, соответствующая эталону `0.2` (IoU 75.3%). Поэтому объекты сопоставляются по геометрии, а не по `nm`.
- В разметке есть ошибки: пропущен объект (машина `0.4`) и есть ложное срабатывание (знак `0.5`).
- Атрибуты тоже расходятся (`weather`, `oncoming`), но на IoU они не влияют.

## Решения

| # | Решение | Обоснование | Автор решения |
|---|---------|-------------|---------------|
| 1 | Итоговая оценка = Σ пересечений / Σ объединений | Ошибка на большом объекте должна влиять сильнее | Условие задачи |
| 2 | Все фигуры приводятся к маскам, IoU считается растровым методом (попиксельно) | У эталона есть только маски, а векторный вариант потребовал бы восстанавливать контур из маски с потерей точности; один способ для bBox и полигонов | Предложил ИИ, принял разработчик после обсуждения |
| 3 | Окружение: `.venv` + `requirements.txt`, без poetry | Небольшой проект без сложных зависимостей | Разработчик |
| 4 | Объекты сопоставляются по геометрии (максимальный IoU), а не по `nm` | `nm` в эталоне и разметке не совпадают | Разработчик |
| 5 | Тип при сопоставлении не учитывается, несовпадение типа отмечается в отчёте | Правильные границы при неправильном типе дают больше информации, чем два нераспознанных объекта | Разработчик; вопрос поставил ИИ |
| 6 | Порога нет: парой считается любое пересечение с IoU > 0 | Разумный порог зависит от того, как будут использоваться результаты, а сырые значения информативнее | Разработчик |
| 7 | Пары выбираются жадно, по убыванию IoU; результат сверяется с венгерским алгоритмом | Жадный алгоритм проще и прозрачнее. Сверка показала, что на этих данных пары совпадают, поэтому в коде оставлен жадный | Разработчик; варианты предложил ИИ, сверку выполнил ИИ по просьбе разработчика |
| 8 | Структура папок эталона и разметки считается одинаковой, пути строятся от имени папки | Чтобы избежать избыточного усложнения кода | Разработчик; ИИ уточнил, что `.images` есть только у эталона |
| 9 | Атрибуты картинки (`weather`) не сравниваются | Задание касается только объектов | Разработчик |
| 10 | Размер кадра хранится в каждом объекте как неизменяемый кортеж | Не нужно передавать по коду отдельную сущность; кортеж исключает случайное изменение общих данных | Разработчик |
| 11 | Маска bBox строится по правилу инструмента разметки: координаты округляются вниз, правая и нижняя граница не включается; `ImageDraw.rectangle` не используется | Pillow включает граничный пиксель, и маска из координат эталона совпадала с его же PNG только на 81–93%. После исправления — совпадение до пикселя | Расхождение нашёл ИИ при сверке; решение исправить принял разработчик, код написал ИИ |
| 12 | `generate_mask` разбит на диспетчер и три метода: `_mask_from_path`, `_mask_from_png`, `_mask_from_bbox` | Выбор способа отделён от реализаций, каждый способ проверяется отдельно и получает только свои аргументы | Идея разбить — разработчик; структуру предложил и написал ИИ |
| 13 | Маска эталона читается по индексу палитры (`np.array(img) > 0`) | `convert("1")` сравнивает яркость с порогом и обнуляет тёмные цвета: маска красного барьера становится пустой. Сравнение по `color` работает, но зависит от лишнего поля | Предложил ИИ |
| 14 | Для всех пар хранятся две матрицы, пересечений и объединений; IoU получается их делением | Итоговая оценка — это Σ пересечений / Σ объединений, а из одной матрицы IoU площади не восстановить | Разработчик; хранить обе матрицы предложил ИИ |
| 15 | Код разбит на модули: `picture_object.py`, `loader.py`, `matching.py`, `report.py`, `main.py` | У модулей разные обязанности; зависимости идут в одну сторону, `matching` не знает про JSON и файлы | Структура — разработчик; названия модулей предложил ИИ |
| 16 | Результат выводится в консоль и в файл; текст отчёта строится одной функцией | Данные исключены из репозитория, и файл позволяет увидеть результат без запуска; общий текст не даёт консоли и файлу разойтись | Разработчик; единый текст предложил ИИ |
| 17 | Результат сопоставления возвращается словарём, а не датаклассом | Структура используется один раз | Разработчик |
| 18 | В отчёте показаны площади объектов и суммы пикселей в итоговой строке | Видно, почему итог взвешенный, а не среднее процентов; проверяющий может пересчитать итог сам | Предложил ИИ, принял разработчик |

## Результат

- 7 пар, 1 пропуск (эталон `0.4`, машина), 1 ложное срабатывание (разметка `0.5`, знак). Во всех парах тип совпадает.
- Итоговая оценка: 8904 / 18063 ≈ **49.3%**.
- Без учёта пропуска и ложного срабатывания вышло бы 49.9%. Оба объекта маленькие и влияют слабо, а итог определяют крупные барьеры с IoU 0.40 и 0.49. Это и есть взвешивание по площади, которого требует задание.
- Главная ошибка разметки: оба барьера обведены примерно вдвое больше эталона (4609 px против 2377, 7793 против 3568). Именно они тянут итог вниз.
- Полный отчёт: `report.txt`.

## Проверка

- Пропуски и ложные срабатывания определены верно: они совпадают с выявленными при первичном разборе данных (пропуск — эталон `0.4`, ложное срабатывание — разметка `0.5`).
- Эталон, сравнённый сам с собой, даёт 100% на каждом объекте и в итоге; каждый объект сопоставился сам с собой:

## Ограничения и что можно улучшить

- Из `path` берётся только первый контур (`path[0]`). В текущих данных у всех полигонов ровно один контур. Что означают несколько контуров (отдельные части объекта или дырки), в формате не описано.
- Полигоны разметки растеризуются через `ImageDraw.polygon`, который включает граничные пиксели. Скорее всего, у них то же смещение на пиксель, что было у bBox. Проверить это нельзя: у эталона нет вершин полигонов. Сильнее всего это влияет на маленькие объекты.
- Ни жадный, ни венгерский алгоритм не оптимизируют итоговую метрику. Венгерский максимизирует сумму IoU, где все пары весят одинаково, а итог — это Σ пересечений / Σ объединений, где пары весят по площади. На плотных сценах, где алгоритмы расходятся, выбор алгоритма стоит проверять на конкретных объектах.
- Имя картинки (`road.jpg`) и номер кадра в пути к маскам (`00001`) заданы в коде. Скрипт обрабатывает одну картинку с одним кадром.
- Данные (`annotated/`, `ground_truth/`) не входят в репозиторий. Без них скрипт не запустится, результат можно посмотреть в `report.txt`.
